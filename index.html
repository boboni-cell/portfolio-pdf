Conversational Life Management App

通过 AI 聊天完成日记、记账与日程规划的生活管理产品

02
PROJECT BACKGROUND

为什么做小暖？

市面上的生活管理工具功能齐全，但独居和单身用户仍然"懒得用"——不是缺功能，是缺动机。

工具碎片化
记账一个 App、日程一个 App、日记一个 App——用户需要在三四个工具间切换，每次切换都是放弃的机会。
输入摩擦太大
每笔消费都要打开 App、选分类、填金额。流程越长放弃率越高，一周后用户就不再打开。
缺少陪伴感
独居用户面对的不是"不会用工具"的问题，而是"没有人一起"的孤独。他们需要的不是更聪明的算法。
年纪稍大用户
对复杂 UI 和表格式输入有天然抵触。他们更习惯用说话的方式表达需求，而不是在列表里翻找功能。
03
PROBLEM DEFINITION

为什么聊天、记账、日程、日记要放在一起？

传统工具把生活拆成碎片，小暖把它还原成一条连续的河流——聊天是入口，识别是引擎，归档是结果。

01 聊天是自然入口

用户说"今天买奶茶花了 18"时，不是为了记账，是为了分享。记账只是顺便。把输入动作藏在对话里，摩擦降为零。

02 情绪是上下文

同样一笔消费，开心时和焦虑时含义完全不同。脱离情绪的记账只是数字堆砌，结合情绪的消费才有理解价值。

03 日记是记忆锚点

不是"每天打开日记本写"，而是聊天和消费自动沉淀成可回看的个人历史。记录在发生，不需要刻意去做。

04 提醒是陪伴延伸

提醒不应该像闹钟。它应该像家里人在旁边说一句"该吃饭了"。不是 push，是 gentle nudge——有人在意你的日程。

小暖的生活闭环
用户开口聊天 AI 识别意图与类型 提取金额/时间/情绪 自动归档各模块

传统 App 把聊天、日记、日程、记账拆成四个独立工具，需要用户分别打开、分别填写。小暖把它们串成一个闭环：用户只需要说话，剩下的由 AI 自动分流和处理。同一个对话可以同时产生消费记录、日程提醒和心情日记。

04
TARGET USERS

谁需要小暖？

不是"不会记录"，而是"不想被工具打断"——这才是小暖真正的用户。

U
Primary Persona

独居 / 单身 / 年纪稍大
懒得手动记录的人

"不是学不会记账 App，是每天打开填数字太烦了。如果跟谁说句话就能记好、到时间自动提醒，那才叫真的有用。"

典型场景 独居者的一天

早上喝咖啡花了 28，中午跟朋友约饭 AA 转账，晚上想起后天要交电费——没有人帮忙记，没有人提醒。

典型场景 年纪稍大用户

50-85 岁，手机用得惯但怕复杂。拒绝"记账"，愿意"聊今天花了什么"。对表格式输入天然抵触。

Design Opportunities
01

把输入藏进对话里：用户不需要知道"我在记账"。聊天时随口说出来，系统后台自动提取和分类——零学习成本。

02

让提醒变成"有人在意"：独居用户的孤独感往往在没人提醒的日常里。小暖的提醒不是 push，是"我在帮你记着"。

03

降低认知负担：年纪稍大用户不习惯功能菜单和层级导航。用自然语言交互取代界面操作，说一句就完成。

AI PERSONA DESIGN

小暖是谁？

一个会聊天的生活管家 / 陪伴式记录助手。面向独居、单身男女与年纪稍大的用户——
不需要学记账 App，不需要填表，只要像跟朋友说话一样自然聊天。

角色定位
会聊天的生活管家与陪伴式记录助手。用户把消费、计划和心情在日常对话里说出来，小暖自动理解并整理，省去所有手动输入步骤。
交互方式
用户自然聊天 → 小暖自动识别金额、时间、事项 → 实时归类为消费记录、日程条目或提醒。一句话同时提取多项信息。
语气风格
自然、沉稳、简洁。不带多余语气词，不扮演"姐姐"或"闺蜜"角色。平等、尊重，保持恰到好处的陪伴感。
能力边界
能做：自动记账、日程提取、提醒跟进、生活小结。不做：医疗建议、投资决策、情感咨询、替用户做任何决定。
06
CORE DESIGN STRATEGY

三个核心设计原则

三个原则贯穿小暖的每一个功能决策，构成了与其他 AI 助手的根本差异。

聊天即记录
用户不需要打开记账或日程页面。在聊天中自然说一句，AI 自动提取金额、时间和事项，一句话同时写入多个模块。
例："今天中午和同事吃湘菜花了 86，下周三之前要交方案" → 记账 86 元 + 日程周三提醒，一句完成。
自动整理与归档
用户不需要手动分类。AI 根据上下文自动归类消费类型、识别日程优先级、提取情绪状态，每周自动生成生活小结。
例：一周聊天内容自动生成"本周支出一览"和"心情变化小结"，无需用户做任何操作。
陪伴式提醒
提醒不是冰冷的系统通知，而是"有人在旁边帮你记着"。准时、温和、不说教。用户做完就轻轻翻篇，没做不追责。
例："明天上午有体检，今晚早点休息哦"而不是"⏰ 体检提醒：明早 9:00"。

09
FEATURE DEEP DIVE

聊天 · Chat

聊天是小暖所有功能的唯一入口——用户不需要知道"我在记账"或"我在写日记"，只需要像跟朋友说话一样自然表达。

01
用户触发

用户在日常对话中说出消费金额、时间安排、情绪状态或待办事项，形式完全自由，不需要使用指令格式或关键词。

02
AI 处理

实时识别对话中的四类信息：金额与类别（记账）、时间与事项（日程）、情绪关键词（日记）、承诺与截止（待办），自动提取结构化字段。

03
用户结果

一句话可能同时触发多个模块。"中午吃了湘菜 86，下周三交方案" → 记账 86 元餐饮 + 日程周三提醒，用户无感完成两项记录。

设计重点

同一句话可以同时写入记账、日程、日记三个模块——用户不需要区分"我现在在记账"还是"我在聊天"。零认知负担，零学习成本。

10
FEATURE DEEP DIVE

日记 · Diary

日记不是"写"出来的，是"发生"出来的——小暖从每日聊天中提取事件和情绪，自动生成可编辑的日记草稿。

01
用户触发

用户在日常聊天中分享今天做了什么、心情如何、遇到什么事。不需要说"写日记"，只需自然表达——"今天跑完步感觉整个人活过来了"。

02
AI 处理

提取对话中的事件描述、情绪关键词和时间线，匹配当天的消费记录和日程条目，自动生成结构化日记草稿——时间轴 + 事件摘要 + 心情标签。

03
用户结果

打开日记页，已经写好的草稿等着确认——可以原样保存、补充细节、添加图片，或删掉重写。写日记从"每天找时间写"变成"看一眼确认就好"。

设计重点

日记不是"记录今天做了什么"，而是"让今天被在意地记住了"。自动生成降低启动阻力，可编辑保留用户掌控感——写日记从负担变成确认。

11
FEATURE DEEP DIVE

日程 · Schedule

日程不应该需要"录入"——用户随口说的时间承诺就是日程，小暖负责把它变成准确的时间轴和温和的提醒。

01
用户触发

用户说"下周三之前要交方案""明天下午两点约了牙医""周末想去看展"。形式随意，时间可以是精确点也可以是模糊范围。

02
AI 处理

从对话中提取日期/时间、事项描述、紧急程度、关联条件（"之前""之后""左右"）。模糊时间自动解析："下周"= 周一，"下周三之前"= 周二提醒。

03
用户结果

日程页展示自动生成的时间线，用户可调整提醒时间或补充备注。到期时小暖温和提醒，用户做完轻轻翻篇，没做不追责。

设计重点

"下周"自动解析为周一，"下周三之前"自动设为周二提醒——模糊时间表达转为精确日程，用户不用算日期和星期几。

12
FEATURE DEEP DIVE

记账 · Wallet

记账的最大阻力是打开 App、选分类、填金额——小暖把它变成一句话的事，你只管说花了什么。

01
用户触发

用户说"今天中午吃了湘菜 86""刚充了 200 话费""奶茶 18"。可以是完整句子也可以是碎片信息，随时说随时记，不需要选分类。

02
AI 处理

提取金额、消费类别（餐饮/购物/交通/娱乐等）、时间、备注，自动入账归类。连续多条消费自动合并，同一天消费生成日汇总与超支提醒。

03
用户结果

记账页展示当日/本周/本月收支，按类别可视化。用户看到的不是冷冰冰的数字表，而是"本月餐饮比上月少了 200"这样的生活洞察。

设计重点

你只管说花了什么，剩下的交给小暖。不记错（AI 校验金额和类别）、不重复（同一条对话不重复入账）、不漏项（识别到消费意图即使没说金额也会追问确认）。

13
TESTING & ITERATION

测试发现与迭代决策

三个迭代循环，每次发现一个真问题、做出一个明确决策、产生一个可验证的结果——没有"持续优化"这种空话。

第一轮 · 自测（30 天）
设计者本人作为唯一用户连续使用一个月。每天记账、写日记、设日程，模拟独居用户的生活节奏。目标不是找 bug，是感受"哪里让我不想继续用"。
第二轮 · 家人测试
邀请 50-75 岁的家庭成员作为真实用户。他们不关心 AI 原理，只在意"说一句话能不能帮我记好"。这次测试暴露了最大的认知摩擦点。
第三轮 · Beta 外部反馈
在小范围微信群中发布 Beta 版本，收集独居和单身用户的日常使用反馈。重点观察"他们会在什么时候放弃使用"。
迭代 01 · 记账分类不准确

问题现象：AI 把"奶茶 18"记成"购物"而非"餐饮"，把"打车 35"记成"交通"但混入了"滴滴月卡充值"。

用户反馈："我说奶茶，它给我记成购物，我还得手动改，那跟普通记账 App 有什么区别？"

修改方案：在 System Prompt 中增加三级分类关键词映射表（奶茶→餐饮→饮品），识别到模糊类别时追加确认而非直接入账。

设计结果：分类准确率从约 65% 提升至约 92%。模糊消费场景（团购、转账）改为追问"这算餐饮还是购物？"。

迭代 02 · 对话提取遗漏待办

问题现象：用户说"下周三之前要交方案，这周末得加班赶一下"，AI 只提取了"下周三交方案"，漏掉了"周末加班"这条隐含日程。

用户反馈："我以为它帮我记了周末要加班，结果只有周三的提醒，还得我自己再设一个。"

修改方案：在识别逻辑中增加"因果链解析"——当一句话中出现"所以/得/需要/那就要"等因果连接词时，将后续内容也作为独立待办提取。

设计结果：因果链中的隐含待办不再遗漏。用户确认后分条入日程，避免一个提醒里塞了多项任务。

迭代 03 · 首次使用认知门槛

问题现象：新用户打开 App 后不知道该干嘛——首页聚合了四个模块，但没有一个明确的"开始"动作。

用户反馈："我知道它能记账、能写日记，但我第一句话该说什么？我是不是要先设置什么东西？"

修改方案：新用户首次进入时，小暖主动发送三条引导消息并提供可点击示例（"今天花了什么""今天心情怎么样""帮我记个提醒"），降低第一句话的心理门槛。

设计结果：首次会话启动率明显提升。用户看到示例后直接点击或照着说，不再停留在首页不知所措。

PROACTIVE CARE SYSTEM

小暖小贴士 · 主动关怀

小暖不是被动等待用户提问的工具，而是会根据时间、用户状态和行为历史，主动给出恰当的关怀提醒——不打扰、不频繁、恰到好处。

01
时间触发

根据时间段和用户作息模式触发。深夜检测到用户仍在活跃 → 发送休息提醒。早上首次打开 → 问候 + 今天天气和日程预览。午饭后 → 提醒可以小睡片刻。

02
状态触发

基于用户近期的消费、日记、日程数据判断状态。连续三天日记出现负面情绪词 → 轻轻问一句。本周消费大幅超过往周均值 → 温和提醒但不评判。

03
行为触发

基于用户操作行为判断。用户连续多天未打开日记功能 → 某天聊天中主动提一句"最近要不要写一篇？"。用户刚设完一周日程 → 顺势提醒"这周排得很满，记得留点休息时间"。

话术示例
深夜活跃 → "还没睡呀，明天还要早起吧？" 连续加班 → "今天也辛苦了，记得喝杯热水" 消费突增 → "这周花了比平常多，需要帮你理一下吗？"
CARE FLOW 用户状态数据采集 → AI 判断触发条件 → 匹配话术模板 + 个性化参数 → 生成贴士推送

设计原则：每天最多推送 1-2 条，不超过 3 条。用户可关闭。不追责、不催促、不制造焦虑。

THE PROBLEM

AI 视频的三大痛点

PAIN 01
角色一致性失控

同一个人物在不同镜头中容易变脸、换发型、服装细节漂移，短视频一旦连续播放就会立刻出戏。

我的处理
  • 先用 ChatGPT Image 2 生成角色设定图
  • 沉淀角色外貌、服装、气质关键词
  • 每个镜头都复用同一角色锚点
PAIN 02
场景与镜头断裂

AI 单次生成很容易只追求"好看的一帧"，但漫剧需要空间关系、镜头角度和情绪节奏连续。

我的处理
  • 先建立场景图与镜头类型库
  • 把剧情拆成可执行的分镜单元
  • 用统一模板约束景别、动作和情绪
PAIN 03
生成成本不可控

如果每个镜头都靠临时试错，素材越多越混乱，返工会吞掉大部分时间和 API 成本。

我的处理
  • 把角色、场景、分镜拆成独立资产
  • 用脚本批量组织 Prompt 与请求参数
  • 保留可复用素材，降低后续边际成本
核心判断 AI 漫剧不是单纯"生成视频"，而是先建立可复用资产，再把文本拆成稳定生产流程。
设计目标 让角色、场景、分镜、视频生成四个环节可以被管理、复用和迭代。

VIDEO GENERATION

视频生成流程

我把漫剧生产拆成"可控资产 + 自动分镜 + 批量生成 + 人工复核"的流程。重点不是一次性生成炫技画面，而是让每一集都能稳定复用角色、场景和镜头规则，形成真正可以连续产出的短剧流水线。

1
分镜拆解

Python 脚本读取剧本，按情节拆分为独立镜头单元，标记角色和场景。

2
参考图匹配

根据镜头需求，从角色库和场景库自动匹配对应的参考图。

3
提示词构建

拼接角色描述、场景、景别、动作和情绪，形成可调用的 API 指令。

4
API 调用生成

传入参考图和提示词，批量生成 4-15 秒视频片段。

5
质检与合成

筛选可用镜头，统一字幕、节奏和音效，输出完整漫剧片段。

24
PROMPT & API

Prompt / API 调用流程

这里的 Prompt 不是临时写一句描述，而是把故事理解、角色资产、场景资产和镜头语言编码成稳定参数。它决定了 AI 生成是否能从"随机好看"进入"可导演、可复盘、可批量生产"。

// Prompt 构建模板

角色描述：
"女主江妹，黑色长发，白色衬衫，蓝色牛仔裤…"

场景描述：
"工地背景，白天，远处有起重机…"

镜头指令：
"中景，转头看向顾决，表情惊讶…"

时长约束：
"4-8 秒，慢动作"
REQUEST分镜 JSON → Prompt 模板 → 参考图 URL → Seedance 请求体
RETRY按镜头顺序调用 API，不合格镜头自动标记重试
ARCHIVE生成结果按剧集、角色、场景归档，方便后续复用

LESSONS & FUTURE

踩坑总结与未来优化

踩坑总结
角色一致性

即使使用参考图，不同镜头角度仍会出现面部偏差。解决：增加面部特征的提示词约束。

镜头连贯性

每个镜头独立生成导致动作不连贯。解决：设计镜头间的过渡逻辑。

成本控制

题材选择影响观众留存，算力成本需要和内容价值匹配。

未来优化
  • 优化角色一致性算法
  • 增加更多镜头类型
  • 开发批量生成功能
  • 探索更多题材方向
  • 降低单集制作成本
